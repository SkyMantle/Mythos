# Скан ефіру: аналогове FPV-відео, 400 МГц — 6 ГГц

Серверний застосунок: сканує діапазон, знаходить передачі аналогового
композитного відео, декодує з них картинку і віддає все у веб-консоль.
Ставиться на Raspberry Pi 5 з bladeRF 2.0 micro xA4; доступ з іншого
комп'ютера — через ZeroTier.

Приймач працює тільки на прийом. Нічого не випромінює.

Цифри нижче — з поставленого `config.yaml`. Ключі з коментарями живуть
там; цей файл пояснює намір, обмеження і типові пастки. Розширений
проєктний опис — `fpvscan-technical.pdf` у корені репозиторію Mythos.

---

## Драйвер

`fpvscan/sdr/bladerf.py` — ctypes напряму до `libbladeRF`, тієї самої
бібліотеки, якою користується `bladeRF-cli`. Формат потоку SC16_Q11,
синхронний прийом, ручне керування підсиленням, доступ до міток часу
і до профілів швидкої перебудови.

Робочий драйвер один — `bladerf`. `file` і `sim` існують тільки щоб
можна було міняти алгоритми обробки, не тягаючись щоразу до стенду.

## Розробка на Windows

Плата працює на Windows так само, як на Pi — це та сама бібліотека.
Команди нижче — з каталогу `fpvscan/`:

```powershell
:: один раз: інсталятор Nuand bladeRF (дає драйвер + bladeRF.dll)
py -3.11 -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt

python scripts\bringup.py -f 5800     :: підняття на стенді з VTX
python run.py                         :: http://127.0.0.1:8080
```

Якщо щось не заводиться — спершу:

```powershell
python scripts\doctor.py
```

Він перевіряє по черзі розрядність Python, наявність бібліотеки на
диску, її залежності, завантаження, видимість плати і стан FPGA, і
зупиняється на першому, що не так.

Бібліотека шукається у стандартних каталогах установки, у реєстрі та
в `PATH`. Якщо лежить деінде — `--lib "C:\...\bladeRF.dll"`, або
`sdr.lib_path` у конфізі, або змінна оточення `BLADERF_LIB_DIR`.

Дві типові пастки на Windows. Перша: `bladeRF.dll` є, але поруч немає
`libusb-1.0.dll` — тоді Windows каже «не знайдено модуль» саме про
`bladeRF.dll`, і виглядає це так, ніби її немає. Друга: з Python 3.8
ctypes більше не шукає залежності DLL по `PATH`, тому каталог треба
називати явно — це вже зроблено в завантажувачі.

Коли плати немає під рукою (наприклад, правиш декодер у дорозі),
є `--driver sim` із синтезованим композитним сигналом і `--file` для
відтворення записаного ефіру. Це допоміжні режими, не основні.

### Cloud Agent / Linux без плати

У хмарному середовищі `libbladeRF` недоступна. Інсталятор
`.cursor/install.sh` (з кореня репозиторію) ставить venv і залежності;
консоль піднімається на симуляторі:

```bash
bash .cursor/install.sh
cd fpvscan && ./.venv/bin/python run.py --driver sim --port 8080
```

`file`-режим так само працює без заліза: `--file caps/vtx.cf32`.
Запис за замовчуванням крутиться по колу (`sdr.loop: true`).

## Робота з реальним стендом

Порядок, який економить найбільше часу: **записати ефір один раз,
відлагоджувати нескінченно**.

```bash
# на Pi, антена наведена на увімкнений передавач
python scripts/bringup.py -f 5800          # підбір підсилення + перевірка тракту
python scripts/bench_retune.py            # реальна швидкість перебудови
python scripts/record.py -f 5800 -s 40 -d 3 -o caps/vtx_f4.cf32
```

`bringup.py` проходить чотири етапи — рівень, спектр, рядкова частота,
декодування кадру — і на кожному, якщо щось не так, пише що саме
дивитись. Це швидше, ніж гадати за веб-консоллю.

Файл (три секунди на 40 Мвідл/с ≈ 960 МБ) перетягуєш на Windows і далі
працюєш офлайн, з тим самим сигналом і відтворюваним результатом:

```powershell
python scripts\bringup.py --file caps\vtx_f4.cf32
python run.py --file caps\vtx_f4.cf32        # уся консоль на записі
```

Запиши кілька різних умов: впритул, здалеку, з перешкодою, з двома
передавачами одночасно. Це і буде набір, на якому підбираються пороги
детектора — по симулятору вони налаштовуються лише приблизно.

Якщо консоль мовчить, а неясно, чи зламався веб, чи сам тракт —
`scripts/headless.py` ганяє рушій без uvicorn і друкує спектри / кадри /
знахідки в термінал:

```bash
python scripts/headless.py --driver sim --secs 20
python scripts/headless.py --lock 5800 --secs 15
python scripts/headless.py --debug --secs 30   # кожен кандидат і причина
```

### На що дивитись першого разу

**Підсилення.** Головна пастка. Впритул до передавача bladeRF заганяє
АЦП у насичення, а обрізаний сигнал дає на виході не картинку, а
широкосмугове сміття — і при цьому у спектрі все виглядає чудово.
`bringup.py` показує частку обрізаних відліків; тримай її на нулі, а
пік у межах −25…−10 дБ від шкали. АРП (`agc: true`) зручна для пошуку,
але для декодування шкідлива: вона підстроюється всередині кадру і
пливе яскравість.

**Bias-T.** У поставленому конфігу `bias_tee: true`. LNA на антені дає
свої ~15–20 дБ поверх `gain_db`. Без компенсації АЦП знову кліпає, і
декодер малює смуги замість картинки. Тому при увімкненні bias-tee
рушій зрізає `gain_db` на `bias_tee_gain_offset_db` (у yaml — 15).
Кнопка Bias-T у консолі робить те саме на льоту.

**Смуга.** Канал 5.8 ГГц займає 20–27 МГц. Якщо `video.sample_rate`
менша, декодер зріже бічні смуги і кадр не збереться. Поставлений
конфіг тримає **35 Мвідл/с** і для свіпу, і для LOCK — компроміс між
покриттям каналу і стабільністю USB. 40 Мвідл/с надійніше по смузі;
61.44 — стеля bladeRF xA4, але через USB 3.0 потік уже на межі, стеж
за лічильником зривів у консолі.

**Витік гетеродина.** Постійне зміщення АЦП сидить рівно в центрі
смуги, тобто посеред каналу, і псує яскравість. Лікується
`video.lo_offset_hz`: ФАПЧ ставиться збоку від каналу, а зсув
робиться цифрово. Ціна — частина смуги йде на зміщення, тому
вмикай разом із підвищеною `sample_rate` (наприклад 61.44 МГц і
зміщення 8 МГц). Якщо `|lo_offset| + channel_bw/2` вилазить за
`0.45 * fs`, рушій обнуляє зсув — інакше каналайзер накладеться сам
на себе.

**Полярність.** У якому боці вершина синхроімпульсу — залежить від
передавача. Декодер пробує обидва варіанти і бере той, де
міжсинхронні інтервали лягають рівніше, тож тут нічого робити не
треба.

**Зриви потоку USB.** Ненульовий лічильник — це майже завжди або
кабель не USB 3.0, або живлення Pi. Плата з антеною на повній смузі
їсть помітно; Pi 5 потрібен БЖ на 5 В / 5 А.

**Частота дискретизації плати.** libbladeRF часто віддає сусіда
запитаної частоти (наприклад 34 999 872 замість 35 000 000). Рушій
переписує `scan.sample_rate` і `video.sample_rate` фактичним
значенням і далі порівнює з допуском **1 Гц**. Точне `!=` рвало б
нитку читання IQ щокадру, скидало б `DecodeState` і картинка ніколи
б не утрималась.

**YAML.** `400.0e6` без знака в експоненті YAML 1.1 читає як рядок.
`config.load` приводить такі рядки до float, тож у конфігу можна
писати і `e6`, і `e+6`. Без цього порівняння і ділення дають дивні
помилки далеко від причини.

## Розгортання на Pi 5

Репозиторій на GitHub — **Mythos**, застосунок лежить у підкаталозі:

```bash
git clone <repo> && cd Mythos/fpvscan
./deploy/install_pi.sh
```

Скрипт ставить `libbladerf2` / FPGA xA4, користувача `fpv`, копіює
дерево в `/opt/fpvscan` і вмикає systemd-юніт
`deploy/fpvscan.service` (`Nice=-5`, група `plugdev`).

Далі ставиш `zerotier-one`, приєднуєш вузол до мережі — і консоль
доступна на `http://<zerotier-адреса>:8080`. Порт назовні не
відкривається взагалі: `web.host` можна лишити `0.0.0.0`, бо єдиний
маршрут до нього — через ZeroTier, але надійніше прописати саме
ZeroTier-адресу вузла.

Якщо порт зайнятий (друга копія тримає плату), `run.py` одразу
виходить.

Живлення: bladeRF на повній смузі їсть помітно, Pi 5 потребує
БЖ на 5 В / 5 А. Кабель — обов'язково USB 3.0, інакше потік рветься.

## Як воно працює

Три режими. Свіп і декодування крутить одна робоча нитка; у LOCK
окремо крутиться нитка читання IQ.

**SWEEP** — прохід `scan.start_hz` … `scan.stop_hz` (400 МГц … 6 ГГц).
Крок, якщо `step_hz: 0`, рахується так, щоб канал не розрізався
на стику двох вікон:

```
step = max(fs * 0.25, fs * 0.9 - channel_bw_hz / 2)
```

На поставлених 35 Мвідл/с і `channel_bw_hz: 10e6` це ≈ **26.5 МГц**.
На кожному кроці — усереднена періодограма, оцінка шумової підлоги
медіаною, пошук неперервних ділянок вище підлоги. Кандидати з
шириною смуги поза **2.5…35 МГц** відкидаються одразу: аналогове
відео туди не вміщується. Нижню межу тримаємо нижче 4 МГц, бо
реальний передавач на стенді давав ~4.3 МГц і жорсткий поріг його
зрізав.

Пріоритетні діапазони (433 / 900 / 1G2 / 2G4 / 3G3 / 5G8) у коді
можуть чергуватись із суцільним проходом 1:1, але в поставленому
yaml `priority_bands: false` — іде лише суцільний скан.

**INSPECT** — головна частина. Широка смуга сама по собі не доводить
нічого: так само виглядає Wi-Fi, LTE чи стрибуча завада. А от рядкова
розгортка залишає в демодульованому сигналі дуже вузьку спектральну
лінію на 15 625 Гц (PAL) або 15 734 Гц (NTSC) з гармоніками. Її
наявність — практично безпомилкова ознака композитного відео, і саме
за нею фільтруються кандидати. Для вимірювання потрібні десятки
періодів рядка, тому робиться окреме захоплення на `inspect_ms`
(25 мс), не 2–3 мс зі свіпового буфера.

Знахідки з центрів ближче ніж 6 МГц зливаються в одну. У список
консолі потрапляють лише після `confirm_hits` підтверджень (у yaml
— 2): одноразовий спалах у шумі не показуємо.

**LOCK** — утримання каналу. Приймач читає безперервно в
`IQRingBuffer` (типово `ring_seconds: 0.5`); робоча нитка бере
знімки по `capture_ms` (80 мс, коротше — коли трекінг уже тримає
рядкову) і не блокує плату на час декодування. Далі: каналайзер
(з цифровим AFC-зсувом), ЧМ-дискримінатор, корекція передспотворень,
декодер CVBS (полярність, поріг синхри, порядковий генлок / TBC,
кадрова синхра, вирізання активної частини) і **WebP** у браузер.

Цифрова AFC (`video.afc`) крутить вікно каналайзера, а не ФАПЧ
плати. Фізична перебудова — рідкісна: коли накопичений зсув
перетинає `afc_recenter_frac` ліміту (типово 0.75). Раніше AFC
входив у частоту настройки щокадру, `_start_reader` скидав
`DecodeState`, і картинка розсипалась на вільнонесучому VTX.

Після декоду: рухомо-адаптивне усереднення (`average` +
`motion_thresh` — фон чиститься, рух і текст не змазуються),
авторівні (`auto_levels`) і горизонтальна апертурна корекція
(`sharpen`). Поріг `min_lines` типово 200: одне поле NTSC коротше
за PAL, 250 відсікало б живі кадри.

Кольорову піднесучу навмисно не декодуємо. У реальному перехопленні
відношення сигнал/шум зазвичай таке, що яскравість ще читається, а
колірна синхронізація вже розсипається — яскравісна картинка дає все
потрібне для розпізнавання обстановки і коштує вдесятеро дешевше.

### Автоперегляд і консоль

`auto_peek: true` — знайшли канал із впевненістю ≥ `auto_peek_min_conf`
(0.6) → показали картинку `auto_peek_secs` (5 с) → повернулись до
свіпу. Той самий канал не чіпаємо частіше ніж `auto_peek_cooldown_s`
(60 с). Ручне утримання це не чіпає: поки оператор став на канал
кнопкою або Enter у полі МГц, свіп не відновлюється, доки не
натиснуть «Сканувати».

Консоль: Сканувати / Очистити / Знімок / Запис / Bias-T / стати на
МГц / ±0.5 МГц. Enter у полі частоти вішається **один раз** при
завантаженні сторінки, не на кожному heartbeat — інакше після години
роботи одна клавіша шле сотні `lock` і рве декодер та запис.

Знімки — `out/photos/` (WebP). Відеозапис — лише з LOCK, через
ffmpeg у `out/video/` (H.264, `rec_*` у yaml). Зміна режиму зупиняє
запис. Якщо ffmpeg немає — консоль пише помилку, сервер живе далі.

Події рушія: `state`, `spectrum`, `detection`, `frame`, `notice`.
`candidate` йде лише при `scan.debug_candidates` (користується
`headless.py --debug`; веб їх ігнорує). Якщо WebSocket мовчить >4 с,
консоль підхоплює стан через `GET /api/state`.

## HTTP API

Локальна консоль — єдиний клієнт; контракт такий, якщо пишеш свій.

| Метод | Шлях | Команда рушія |
|-------|------|----------------|
| GET | `/` | `index.html` |
| GET | `/api/state` | знімок стану |
| POST | `/api/lock/{freq_hz}` | `lock` |
| POST | `/api/sweep` | `sweep` |
| POST | `/api/snapshot` | `snapshot` |
| POST | `/api/record/{start\|stop}` | `rec_start` / `rec_stop` |
| POST | `/api/bias_tee/{on\|off}` | `bias_tee` |
| POST | `/api/clear` | `clear` |
| WS | `/ws` | сервер → клієнт; клієнт лише тримає канал |

`run.py`: `-c/--config`, `--driver bladerf\|file\|sim`, `--file`,
`--port`, `--lib`.

## Де межа продуктивності

Найгарячіше місце раніше був `demod.shift`: `np.exp` від complex128
на повному (ще недецимованому) потоці ≈ 90 мс на кадр. Зараз зсув
йде через цілочисельний фазовий акумулятор і `cos`/`sin` у float32
≈ 10 мс. `fm_demod` (`arctan2` по масиву) лишається дорогим:
`scripts/selftest.py` на повному 30 Мвідл/с без каналайзера бере
~130 мс на 120 мс ефіру. У LOCK спочатку ріжеться смуга, тож
дискримінатор бачить уже децимований сигнал.

Ядра Cortex-A76 на Pi 5 повільніші приблизно втричі за контейнер
розробки, тож у реальному часі безперервно демодулювати 30+ Мвідл/с
чистим numpy все одно не вийде.

Тому LOCK свідомо працює зі шпаруватістю (`idle_ms: 10` у yaml) і
з кільцевим буфером: приймач не простоює, поки рахується кадр, але
CPU між знімками видихає. Це дає порядку кількох кадрів на секунду.
Для розвідки обстановки цього вистачає, для плавного відео — ні.

Шляхи прискорення, за зростанням вартості:

1. `numba` або невелике розширення на C для дискримінатора і
   ресемплінгу рядків — реалістично 5–10×, найдешевший крок;
2. профілі швидкої перебудови (`quick_tune: true`). Код готовий, але
   чи працює це на конкретній збірці libbladeRF для xA4 — перевіряє
   `scripts/bench_retune.py`. Якщо профілі знімаються не для всіх
   частот, лишай `false`: звичайної перебудови для FPV вистачає, бо
   час проходу все одно визначає не вона, а захоплення відліків;
3. винести оцінку спектра у FPGA Artix-7 на самій платі — тоді
   на Pi приїжджають уже готові вектори потужності, і центральний
   процесор звільняється повністю під декодування.

`scan.fast_channelizer` (типово вимкнений) у INSPECT вмикає дешеве
прямокутне усереднення замість FIR-децимації. Для класифікатора
рядкової цього зазвичай досить.

## Куди складаються результати

Усе, що створює сама програма, лягає в `fpvscan/out/`, а не в
поточний каталог запуску (`fpvscan/paths.py`):

```
out/photos/    знімки (WebP)
out/video/     записи H.264
out/caps/      сирий ефір .cf32 + .json
out/logs/
```

`scripts/record.py -o …` пише туди, куди сказали: відносний шлях
із каталогом лишається як є (`caps/vtx_f4.cf32` поруч зі скриптом).

```bash
python run.py --driver sim --port 8080
```

`selftest.py` пише `scripts/decoded.png`: якщо видно градаційні смуги —
весь тракт живий. Окремого pytest у `requirements.txt` немає; файл
тестів ганяється як скрипт.

## Структура

Шляхи від каталогу `fpvscan/`:

```
run.py                  точка входу
config.yaml             усі параметри (коментарі = довідка по ключах)
fpvscan/
  bands.py              плани діапазонів, сітка каналів 5.8 ГГц
  engine.py             SWEEP / INSPECT / LOCK
  iqbuffer.py           кільцевий буфер IQ для LOCK
  paths.py              out/{photos,video,caps,logs}
  recorder.py           H.264 через ffmpeg
  sdr/base.py           інтерфейс джерела IQ
  sdr/sim.py            симулятор ефіру
  sdr/bladerf.py        драйвер bladeRF: ctypes -> libbladeRF
  sdr/factory.py        вибір джерела за конфігом
  sdr/file.py           відтворення записаного ефіру
  dsp/spectrum.py       періодограма, шумова підлога, зайняті смуги
  dsp/demod.py          зсув, каналайзер, дискримінатор, класифікатор
  dsp/cvbs.py           декодер композитного відео в растр
  web/                  FastAPI + консоль оператора
scripts/selftest.py     наскрізна перевірка без заліза
scripts/doctor.py       діагностика: бібліотека, плата, FPGA
scripts/bringup.py      первинне підняття заліза на стенді
scripts/bench_retune.py замір швидкості перебудови
scripts/record.py       запис ефіру у файл
scripts/headless.py     рушій без веба (діагностика тракту)
tests/test_engine_lock.py  регресія LOCK і консолі
deploy/                 systemd-юніт і скрипт розгортання
```
