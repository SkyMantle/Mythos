# Скан ефіру: аналогове FPV-відео, 400 МГц — 6 ГГц

Серверний застосунок: сканує діапазон, знаходить передачі аналогового
композитного відео, декодує з них картинку і віддає все у веб-консоль.
Ставиться на Raspberry Pi 5 з bladeRF 2.0 micro xA4; доступ з іншого
комп'ютера — через ZeroTier.

Приймач працює тільки на прийом. Нічого не випромінює.

Параметри — у `fpvscan/config.yaml` (коментарі там є джерелом правди
по ключах). Цей файл пояснює намір, архітектуру і типові пастки.

---

## Драйвер

`fpvscan/sdr/bladerf.py` — ctypes напряму до `libbladeRF`, тієї самої
бібліотеки, якою користується `bladeRF-cli`. Формат потоку SC16_Q11,
синхронний прийом, ручне керування підсиленням, доступ до міток часу
і до профілів швидкої перебудови.

Робочий драйвер один. `file.py` і `sim.py` існують лише щоб міняти
алгоритми, не тягаючись щоразу до стенду.

## Розробка на Windows

Плата працює на Windows так само, як на Pi — це та сама бібліотека:

```powershell
:: один раз: інсталятор Nuand bladeRF (дає драйвер + bladeRF.dll)
py -3.11 -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt

python scripts\bringup.py -f 5800     :: підняття на стенді з VTX
python run.py                         :: http://127.0.0.1:8080
```

Якщо щось не заводиться — спершу:

```powershell
python scripts\doctor.py
```

Він перевіряє по черзі розрядність Python, наявність бібліотеки на
диску, її залежності, завантаження, видимість плати і стан FPGA, і
зупиняється на першому, що не так.

Бібліотека шукається у стандартних каталогах установки, у реєстрі та
в `PATH`. Якщо лежить деінде — `--lib "C:\...\bladeRF.dll"`, або
`sdr.lib_path` у конфізі, або змінна оточення `BLADERF_LIB_DIR`.

Дві типові пастки на Windows. Перша: `bladeRF.dll` є, але поруч немає
`libusb-1.0.dll` — тоді Windows каже «не знайдено модуль» саме про
`bladeRF.dll`, і виглядає це так, ніби її немає. Друга: з Python 3.8
ctypes більше не шукає залежності DLL по `PATH`, тому каталог треба
називати явно — це вже зроблено в завантажувачі.

## Розробка без плати (Linux / Cloud Agent)

У хмарному агенті bladeRF немає. `.cursor/install.sh` ставить venv
і залежності; консоль піднімається симулятором:

```bash
bash .cursor/install.sh
cd fpvscan
./.venv/bin/python scripts/selftest.py          # тракт без заліза
./.venv/bin/python tests/test_engine_lock.py    # регресія LOCK/fs
./.venv/bin/python run.py --driver sim --port 8080
```

`--driver sim` синтезує композитне ЧМ-відео (типово борт на 5800 МГц
NTSC і на 1280 МГц PAL плюс вузькі завади). `--file caps/….cf32`
відтворює записаний ефір. Обидва режими — допоміжні, не польові.

Щоб відділити «мовчить обробка» від «мовчить веб»:

```bash
./.venv/bin/python scripts/headless.py --driver sim --secs 20
./.venv/bin/python scripts/headless.py --driver sim --lock 5800 --secs 10
```

Якщо в headless є спектри й кадри, а браузер порожній — дивись порт,
WebSocket і статику, не DSP.

## Робота з реальним стендом

Порядок, який економить найбільше часу: **записати ефір один раз,
відлагоджувати нескінченно**.

```bash
# на Pi, антена наведена на увімкнений передавач
python scripts/bringup.py -f 5800          # підбір підсилення + перевірка тракту
python scripts/bench_retune.py            # реальна швидкість перебудови
python scripts/record.py -f 5800 -s 40 -d 3 -o caps/vtx_f4.cf32
```

`bringup.py` проходить чотири етапи — рівень, спектр, рядкова частота,
декодування кадру — і на кожному, якщо щось не так, пише що саме
дивитись. Це швидше, ніж гадати за веб-консоллю.

Файл (три секунди на 40 Мвідл/с ≈ 960 МБ) перетягуєш на Windows і далі
працюєш офлайн, з тим самим сигналом і відтворюваним результатом:

```powershell
python scripts\bringup.py --file caps\vtx_f4.cf32
python run.py --file caps\vtx_f4.cf32        # уся консоль на записі
```

Запиши кілька різних умов: впритул, здалеку, з перешкодою, з двома
передавачами одночасно. Це і буде набір, на якому підбираються пороги
детектора — по симулятору вони налаштовуються лише приблизно.

Результати (знімки, ролики, сирий ефір) складаються в `fpvscan/out/`
(`photos/`, `video/`, `caps/`), а не в поточний каталог запуску.

### На що дивитись першого разу

**Підсилення.** Головна пастка. Впритул до передавача bladeRF заганяє
АЦП у насичення, а обрізаний сигнал дає на виході не картинку, а
широкосмугове сміття — і при цьому у спектрі все виглядає чудово.
`bringup.py` показує частку обрізаних відліків; тримай її на нулі, а
пік у межах −25…−10 дБ від шкали. У консолі `clip` понад 0.1% —
насичення: знахідки нижче можуть бути продуктами інтермодуляції.
АРП (`agc: true`) зручна для пошуку, але для декодування шкідлива:
вона підстроюється всередині кадру і пливе яскравість.

**Bias-tee / LNA.** Увімкнений LNA на bias-tee додає ~15–20 дБ поверх
`gain_db`. Рушій компенсує це `sdr.bias_tee_gain_offset_db` (типово
15): інакше АЦП кліпає, а декодер малює смуги замість картинки.
Кнопка «Bias» у консолі шле `POST /api/bias_tee/{on|off}`.

**Смуга.** Канал 5.8 ГГц займає 20–27 МГц. Якщо `video.sample_rate`
менша, декодер зріже бічні смуги і кадр не збереться. Типовий конфіг
тримає 35 Мвідл/с (стабільніше по USB, ніж 40). За потреби 61.44 —
але через USB 3.0 потік уже на межі, стеж за лічильником зривів.

**Реальна fs плати.** libbladeRF часто віддає сусідню частоту
(наприклад 34 999 872 замість 35 000 000). Рушій при старті записує
фактичну `src.sample_rate` і в `scan`, і в `video`. У LOCK порівняння
йде з допуском 1 Гц: точне `!=` щокадру гасило б IQ-нитку, скидало
`DecodeState` і картинка ніколи б не утримувалась.

**Витік гетеродина.** Постійне зміщення АЦП сидить рівно в центрі
смуги, тобто посеред каналу, і псує яскравість. Лікується
`video.lo_offset_hz`: ФАПЧ ставиться збоку від каналу, а зсув
робиться цифрово. Ціна — частина смуги йде на зміщення, тому
вмикай разом із підвищеною `sample_rate` (наприклад 61.44 МГц і
зміщення 8 МГц).

**Полярність.** У якому боці вершина синхроімпульсу — залежить від
передавача. Декодер пробує обидва варіанти і бере той, де
міжсинхронні інтервали лягають рівніше, тож тут нічого робити не
треба.

**Зриви потоку USB.** Ненульовий лічильник — це майже завжди або
кабель не USB 3.0, або живлення Pi. Плата з антеною на повній смузі
їсть помітно; Pi 5 потрібен БЖ на 5 В / 5 А.

## Розгортання на Pi 5

```bash
git clone <repo> && cd fpvscan
./deploy/install_pi.sh
```

Скрипт ставить `libbladerf2` + FPGA xA4, venv, systemd-юніт
`fpvscan` (`WorkingDirectory=/opt/fpvscan`, рестарт при падінні).
Далі ставиш `zerotier-one`, приєднуєш вузол до мережі — і консоль
доступна на `http://<zerotier-адреса>:8080`. Порт назовні не
відкривається взагалі: `web.host` можна лишити `0.0.0.0`, бо єдиний
маршрут до нього — через ZeroTier, але надійніше прописати саме
ZeroTier-адресу вузла.

Живлення: bladeRF на повній смузі їсть помітно, Pi 5 потребує
БЖ на 5 В / 5 А. Кабель — обов'язково USB 3.0, інакше потік рветься.

## Як воно працює

Три режими, які перемикає одна робоча нитка (`Engine`). Важка
арифметика живе там; asyncio лише качає події в браузер.

**SWEEP** — прохід `scan.start_hz` … `scan.stop_hz` (типово
400 МГц … 6 ГГц). Крок не дорівнює смузі: канал на стику двох вікон
інакше видно лише навпіл і він не набирає порогу. Формула
`max(fs·0.25, fs·0.9 − channel_bw/2)`; при 35 Мвідл/с і каналі
10 МГц це ≈26.5 МГц. На кожному кроці — усереднена періодограма,
шумова підлога медіаною, зайняті ділянки вище `threshold_db`.
Кандидати вужчі за 2.5 МГц або ширші за 35 МГц відкидаються одразу
(реальний стендовий VTX дав ~4.3 МГц — жорсткі 4 МГц його різали).
`priority_bands: true` чергує суцільний прохід із 433 / 900 / 1G2 /
2G4 / 3G3 / 5G8; у типовому конфігу це вимкнено. Знахідку показуємо
лише після `confirm_hits` (типово 2), інакше спалах шуму потрапляє
в список.

**INSPECT** — широка смуга сама по собі нічого не доводить: так само
виглядає Wi-Fi, LTE чи стрибуча завада. Рядкова розгортка лишає в
демодульованому сигналі вузьку лінію на 15 625 Гц (PAL) або
15 734 Гц (NTSC) з гармоніками. Для вимірювання потрібні десятки
періодів рядка, тому робиться окреме захоплення на `inspect_ms`
(типово 25 мс), не 2–3 мс зі свіпового буфера. Кандидат, що не
набрав `min_confidence`, мовчки відкидається; `debug_candidates:
true` віддає причину в консоль (або в `headless.py --debug`).

**LOCK** — утримання каналу. Приймач читає IQ безперервно в окремій
нитці в кільцевий буфер (`iqbuffer.IQRingBuffer`); робоча нитка лише
бере знімки і декодує. Так приймач не простоює на час DSP і не
губиться фаза синхри між блоками. Далі: каналайзер (зсув + децимація),
цифрова AFC, ЧМ-дискримінатор, корекція передспотворень, декодер
CVBS, WebP у браузер.

`scan.auto_peek` після підтвердженої знахідки сам стає на канал на
`auto_peek_secs` (типово 5 с) і повертається до свіпу. Ручне
утримання це не чіпає: поки оператор не натисне «Сканувати», свіп
не відновлюється. Запис ролика прив'язаний до одного каналу —
команда `sweep` або `lock` його зупиняє.

Кольорову піднесучу навмисно не декодуємо. У реальному перехопленні
відношення сигнал/шум зазвичай таке, що яскравість ще читається, а
колірна синхронізація вже розсипається — яскравісна картинка дає все
потрібне для розпізнавання обстановки і коштує вдесятеро дешевше.

### Тракт картинки в LOCK

Після першого успішного кадру декодер тримає `DecodeState` (період
рядка, полярність, абсолютна позиція кадрової синхри) і далі шукає
наступне поле у вузькому вікні («трекінг»). Три промахи поспіль —
відкат на сліпий пошук. Це прибирає стрибки кадру між знімками з
кільця.

Порядковий генлок (`_genlock_starts`, TBC): старт кожного рядка
рівняється по фактичному фронту синхри в ±6% періоду, а не по
глобальному `t0 + i·period`. Інакше частка відліку похибки за 288
рядків дає нахил вертикалей і діагональний розрив. Кадр обрізається
перед наступним кадровим гасінням — захоплення посеред поля більше
не тягне синхру сусіднього поля в картинку.

Далі, у `config.yaml` → `video`:

| ключ | типово | намір |
|---|---|---|
| `average` | 3 | сила часового усереднення нерухомого фону |
| `motion_thresh` | 24 | поріг «руху» (0…255); нижче — сильніше згладжування |
| `auto_levels` | true | розтяг контрасту за 2-м і 99-м перцентилем (проти «сірої» картинки) |
| `sharpen` | 0.5 | горизонтальна апертурна корекція; 0 — вимк., 0.4–0.8 — помірно |
| `capture_ms` | 80 | стеля захоплення на кадр; після захоплення трекінгу вікно стискається до ~одного поля |
| `idle_ms` | 10 | пауза між знімками (шпаруватість під CPU Pi) |
| `afc` | true | цифрова AFC: зсув вікна каналайзера, не перебудова плати на кожному кроці |

Проста EMA по кадрах давала два артефакти на реальному ефірі:
хмару за рухомим об'єктом і роздвоєння тексту (сусідні знімки —
протилежні поля черезрядка). Тепер усереднюється лише те, що не
зрушилось; краї й рух лишаються різкими.

Фізична перебудова при AFC — рідкісна: лише коли накопичений зсув
перетнув `afc_recenter_frac` (типово 0.75) від ліміту. Інакше кожна
дрібна поправка VTx скидала б `DecodeState` і рвала картинку.

## Консоль і HTTP API

Консоль — одна сторінка (`/`) плюс WebSocket `/ws`. Кадри й спектр
йдуть тільки сокетом; якщо сокет мовчить >4 с, інтерфейс падає на
опитування `GET /api/state`, щоб було видно, що зламався канал, а
не сервер.

| дія | як | API |
|---|---|---|
| стати на знахідку | клік у списку | `POST /api/lock/{freq_hz}` |
| стати вручну | поле МГц + Enter / «Стати» | те саме |
| підкрутити | ±0.5 МГц | повторний `lock` |
| повернутись до свіпу | «Сканувати» | `POST /api/sweep` |
| скинути список і стрічку | «Очистити» | `POST /api/clear` |
| кадр на диск | «Знімок» | `POST /api/snapshot` → `out/photos/*.webp` |
| ролик | «Запис» (лише в LOCK) | `POST /api/record/start\|stop` → `out/video/*.mp4` |
| bias-tee | «Bias» | `POST /api/bias_tee/on\|off` |

Enter на полі частоти вішається **один раз** при завантаженні
сторінки. Раніше обробник ставився всередині `applyState()`, а
heartbeat шле стан кожні 2 с — за годину Enter відправляв сотні
`lock`, кожен скидав декодер і різав запис.

Запис H.264 іде через ffmpeg у stdin окремою ниткою з рівним тактом
(захоплення у нас зі шпаруватістю, інакше ролик «біжить»). Немає
ffmpeg — команда пише помилку в стрічку повідомлень. На Windows
після `winget` PATH оновлюється лише для нового термінала; запасний
вихід — `video.ffmpeg_path`.

## Де межа продуктивності

Найгарячіше місце лишається `fm_demod`: `arctan2` по всьому масиву.
Зсув спектра (`demod.shift`) більше не через `exp` у complex128 —
цілочисельний фазовий акумулятор + `cos`/`sin` у float32; це зняло
десятки мілісекунд з кадру, але дискримінатор усе ще їсть основний
час. На контейнері розробки обробка ~80–120 мс ефіру близька до
реального часу; ядра Cortex-A76 на Pi 5 повільніші приблизно втричі,
тож безперервно демодулювати 30 Мвідл/с чистим numpy не вийде.

Тому LOCK свідомо шпаруватий: знімок з кільця — пауза `idle_ms` —
знімок. Після захоплення трекінгу захоплення стискається до поля
(~20+ мс плюс запас), а не тримає повні `capture_ms`. Виходить
кілька кадрів на секунду. Для розвідки обстановки цього вистачає,
для плавного відео — ні.

Шляхи прискорення, за зростанням вартості:

1. `numba` або невелике розширення на C для дискримінатора і
   ресемплінгу рядків — реалістично 5–10×, найдешевший крок;
2. профілі швидкої перебудови (`quick_tune: true`). Код готовий, але
   чи працює це на конкретній збірці libbladeRF для xA4 — перевіряє
   `scripts/bench_retune.py`. Якщо профілі знімаються не для всіх
   частот, лишай `false`: звичайної перебудови для FPV вистачає, бо
   час проходу все одно визначає не вона, а захоплення відліків;
3. винести оцінку спектра у FPGA Artix-7 на самій платі — тоді
   на Pi приїжджають уже готові вектори потужності, і центральний
   процесор звільняється повністю під декодування.

## Структура

```
run.py                  точка входу (uvicorn + Engine)
config.yaml             усі параметри
.cursor/                Cloud Agent: install.sh, environment.json
fpvscan/
  bands.py              плани діапазонів, сітка каналів 5.8 ГГц
  engine.py             SWEEP / INSPECT / LOCK, зовнішнє command()
  iqbuffer.py           кільце IQ для безперервного читання в LOCK
  recorder.py           H.264 через ffmpeg
  config.py             YAML + приведення "400.0e6" до float
  sdr/base.py           інтерфейс джерела IQ
  sdr/sim.py            симулятор ефіру
  sdr/bladerf.py        драйвер bladeRF: ctypes -> libbladeRF
  sdr/factory.py        вибір джерела за конфігом
  sdr/file.py           відтворення записаного ефіру
  dsp/spectrum.py       періодограма, шумова підлога, зайняті смуги
  dsp/demod.py          зсув, каналайзер, дискримінатор, класифікатор
  dsp/cvbs.py           генлок, трекінг поля, растр, WebP
```
